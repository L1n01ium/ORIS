1. ОБЩАЯ АРХИТЕКТУРА И ПОТОК ЗАПРОСОВ
================================================================================

Код разделён на слои:

    сервлет  ->  сервис  ->  репозиторий  ->  JDBC  ->  PostgreSQL

Зачем такое разделение:
  * сервлет занимается только HTTP: читает параметры, отдаёт страницу/редирект;
  * сервис — бизнес-операции (например, "добавить нескольких пользователей");
  * репозиторий — только SQL;
  * модель User — данные, которые ездят между слоями.

Такое разделение уже есть в проекте до ДЗ (SignUpServlet/SignUpService/
UsersRepository), поэтому новый код ему следует, а не придумывает новую
архитектуру.

Поток №1 — добавление N пользователей:

    GET /servlets_war/save
        SaveServlet.doGet()
            -> usersService.getUsersCount()                (SELECT из app_settings)
            -> req.setAttribute("count", N)
            -> forward на /jsp/save.jsp
                JSTL <c:forEach begin="1" end="${count}"> рисует N блоков полей

    POST /servlets_war/save
        SaveServlet.doPost()
            -> читает count и поля firstName_1 ... phone_N
            -> собирает List<User>
            -> usersService.addUsers(list)
                -> в цикле usersRepository.save(user)      (обычный INSERT)
            -> resp.sendRedirect(contextPath + "/html/saved.html")

    GET /servlets_war/html/saved.html
        -> статическая страница "Пользователи добавлены"

Поток №2 — три выборки:

    GET /servlets_war/selects
        SelectServlet.doGet()
            -> usersService.findByCity("Казань")           (WHERE city = ?)
            -> usersService.findByAgeGreaterThan(18)       (WHERE age > ?)
            -> usersService.findByPhone("+79000000000")    (WHERE phone = ?)
            -> System.out.println(...)  в консоль Tomcat
            -> и тот же текст в браузер (text/plain)

Важно: сервлеты в Java — синглтоны. Tomcat создаёт ОДИН экземпляр класса на
всё приложение и вызывает doGet/doPost из разных потоков одновременно.
Поэтому в полях сервлета нельзя хранить данные конкретного запроса.
В нашем коде поле usersService заполняется один раз в init() и дальше только
читается — это безопасно.


2. БАЗА ДАННЫХ
================================================================================

SQL (файл db/homework3.sql):

    ALTER TABLE account ADD COLUMN IF NOT EXISTS age   INTEGER;
    ALTER TABLE account ADD COLUMN IF NOT EXISTS city  VARCHAR(100);
    ALTER TABLE account ADD COLUMN IF NOT EXISTS phone VARCHAR(30);

    CREATE TABLE IF NOT EXISTS app_settings (
        id    SERIAL PRIMARY KEY,
        name  VARCHAR(100) NOT NULL UNIQUE,
        value VARCHAR(100) NOT NULL
    );

    INSERT INTO app_settings (name, value)
    VALUES ('users_count', '3')
    ON CONFLICT (name) DO NOTHING;

Что здесь важно:

  * Три новых поля добавлены в существующую таблицу account, а не в новую
    таблицу — ТЗ говорит "добавить 3 доп. поля в таблицу", то есть расширить
    текущую.

  * age имеет тип INTEGER. Значение по умолчанию не задано: если возраст не
    указан, код запишет 0 (см. раздел 4.3).

  * city и phone — VARCHAR, потому что это произвольный текст. Для телефона
    можно было взять CHAR/VARCHAR фиксированной длины, но номера бывают в
    разных форматах (+7..., 8...), поэтому VARCHAR(30) универсальнее.

  * app_settings — отдельная таблица "ключ-значение". Число добавляемых
    пользователей берётся из неё, как требует ТЗ ("способ откуда вы это число
    возьмете придумайте сами, главное чтобы из БД").

  * UNIQUE(name) + ON CONFLICT DO NOTHING делают скрипт повторно
    запускаемым: повторный запуск не создаст дубликат строки users_count.
    IF NOT EXISTS у колонок — по той же причине.

Альтернативы для хранения числа:
  * считать количество существующих пользователей: SELECT count(*) FROM account.
    Но это "сколько уже есть", а не "сколько добавить" — ТЗ просит второе.
  * хранить число в отдельной одно-строчной таблице с колонкой amount.
  * хранить в настройках Tomcat / properties-файле. Не подходит: ТЗ требует БД.
  * последовательность (SEQUENCE) — неудобно, число не редактируется как данные.

Плюс app_settings: чтобы изменить количество, достаточно сделать UPDATE,
перекомпиляция и передеплой не нужны.


3. МОДЕЛЬ USER
================================================================================

    @Getter @Setter @NoArgsConstructor @AllArgsConstructor
    @ToString @EqualsAndHashCode @Builder
    public class User {
        private Long id;
        private String name;
        private String surname;
        private Integer age;
        private String email;
        private String password;
        private String city;
        private String phone;
    }

Почему так:

  * Lombok убирает ручные геттеры/сеттеры/конструкторы. @Builder даёт
    читаемое создание объекта: User.builder().name(...).city(...).build().
    В проекте этот стиль уже используется, поэтому новый код ему следует.

  * id — Long, потому что в БД обычно BIGSERIAL/BIGINT. Даже если сейчас
    SERIAL (INTEGER), Long покрывает оба случая.

  * age — Integer, а не int: int не может быть null. В форме возраст
    необязателен, поэтому до сохранения он может быть null, а в save()
    подставляется 0 (см. 4.3).

  * Поля названы так же, как в коде (name, surname), а в БД колонки
    first_name / last_name. Это несоответствие было в проекте изначально;
    мы его сохранили, а преобразование делает приватный метод
    userFromResultSet() в репозитории.

  * Пароль остаётся в модели, хотя формы его не спрашивают: колонка password
    в account, скорее всего, NOT NULL, а старый функционал регистрации
    пароль использует.


4. РЕПОЗИТОРИЙ
================================================================================

4.1. UsersRepository
--------------------------------------------------------------------------------

    public interface UsersRepository extends CrudRepository<User> {
        List<User> findAll();
        int getUsersCount() throws SQLException;
        List<User> findByCity(String city) throws SQLException;
        List<User> findByAgeGreaterThan(int age) throws SQLException;
        List<User> findByPhone(String phone) throws SQLException;
    }

Почему getUsersCount() именно здесь:
  * число берётся из таблицы app_settings, но это одна простая операция;
  * отдельный интерфейс SettingsRepository ради одного метода — лишняя
    сущность, которую пришлось бы объяснять;
  * так в проекте уже принято: один репозиторий — один набор методов.

SQL для числа:

    "select value from app_settings where name = 'users_count'"

  * значение 'users_count' — константа в коде, поэтому здесь обычный
    Statement, как в findAll();
  * если бы значение приходило извне, использовали бы PreparedStatement
    с параметром (как в findByCity и т.п.).

Три метода поиска нужны по ТЗ: "3 доп. поля -> 3 метода -> WHERE".
Они специально разные, а не один универсальный:

  * findByCity           -> WHERE city = ?
  * findByAgeGreaterThan -> WHERE age > ?
  * findByPhone          -> WHERE phone = ?

Почему не один метод findBy(String column, Object value):
  * по ТЗ просят именно 3 метода;
  * имя колонки нельзя передать параметром через ? — пришлось бы клеить
    строку, а это потенциальная SQL-инъекция через имя колонки;
  * три явных метода читаются и проверяются проще.

4.2. UsersRepositoryJdbcImpl — SQL-константы
--------------------------------------------------------------------------------

    SQL_SELECT_ALL         = "select * from account"
    SQL_INSERT             = "insert into account(first_name, last_name, email,
                              password, age, city, phone) values (?, ?, ?, ?, ?, ?, ?)"
    SQL_SELECT_BY_CITY     = "select * from account where city = ?"
    SQL_SELECT_BY_AGE      = "select * from account where age > ? order by age"
    SQL_SELECT_BY_PHONE    = "select * from account where phone = ?"
    SQL_SELECT_USERS_COUNT = "select value from app_settings where name = 'users_count'"

Почему константы: SQL в одном месте, не размазан по методам, легко найти.

Почему PreparedStatement в save и findBy-методах: параметры передаются
отдельно от текста запроса, драйвер сам их экранирует. Склейка строк вида
"where city = '" + city + "'" опасна SQL-инъекцией, поэтому в выполняемых
запросах её нет.

4.3. save()
--------------------------------------------------------------------------------

    Connection connection = dataSource.getConnection();
    PreparedStatement preparedStatement = connection.prepareStatement(SQL_INSERT);
    ... setString / setInt ...
    preparedStatement.executeUpdate();

  * Одна вставка — один executeUpdate, ровно как в исходном save() проекта,
    только добавлены три новых поля.
  * age: statement.setInt(5, entity.getAge() == null ? 0 : entity.getAge()).
    Так сделано потому, что setNull() в проекте не использовался, а setInt(5,
    null) бросил бы NullPointerException. Компромисс: неуказанный возраст
    сохраняется как 0.
  * Остальные поля — setString, как в старом коде.

Почему нет saveAll/батча: см. раздел 12.

4.4. findByCity / findByAgeGreaterThan / findByPhone
--------------------------------------------------------------------------------

Каждый метод повторяет схему, уже знакомую по findAll()/save():

    Connection connection = dataSource.getConnection();
    PreparedStatement preparedStatement = connection.prepareStatement(SQL_...);
    preparedStatement.setString(1, city);   // или setInt(1, age)
    ResultSet resultSet = preparedStatement.executeQuery();
    while (resultSet.next()) { result.add(userFromResultSet(resultSet)); }
    return result;

  * setString для city/phone, setInt для age — по типу колонки;
  * age > ? — строгое "больше", как в названии метода;
  * order by age — чтобы результат был предсказуемым при проверке.

4.5. userFromResultSet()
--------------------------------------------------------------------------------

    String ageAsString = resultSet.getString("age");
    Integer age = ageAsString == null ? null : Integer.parseInt(ageAsString);
    return User.builder()...build();

  * приватный метод класса, чтобы не копировать одинаковый while в четырёх
    местах;
  * getString("age") + Integer.parseInt — вместо getInt()/wasNull(), потому
    что wasNull() в проекте не использовался. getString() для числовой
    колонки возвращает строку или null, и это позволяет отличить NULL от 0;
  * никаких новых библиотек — только JDBC-методы, уже встречавшиеся в коде.

4.6. findAll()
--------------------------------------------------------------------------------

  * оставлен без throws SQLException, потому что его уже вызывает
    существующий UserServlet, который исключение не ловит;
  * SQLException заворачивается в IllegalStateException, чтобы не менять
    сигнатуры старых вызовов;
  * тело изменено минимально: вместо ручной сборки User вызывается
    userFromResultSet().


5. СЕРВИСЫ
================================================================================

    public interface UsersService {
        List<User> getAll() throws SQLException;
        void addUser(AjaxDto form) throws SQLException;
        void addUsers(List<User> users) throws SQLException;
        int getUsersCount() throws SQLException;
        List<User> findByCity(String city) throws SQLException;
        List<User> findByAgeGreaterThan(int age) throws SQLException;
        List<User> findByPhone(String phone) throws SQLException;
    }

Сервис в этой задаче — тонкая прослойка, которая делегирует вызовы
репозиторию. Зачем он нужен:

  * единая точка для бизнес-логики: завтра понадобится проверять email на
    уникальность или хешировать пароль — это место здесь, а не в сервлете;
  * сервлет не знает про JDBC и SQL;
  * так уже устроен проект (SignUpService, UsersService).

addUsers():

    for (User user : users) {
        usersRepository.save(user);
    }

  * обычный цикл и уже существующий save();
  * никаких новых методов JDBC;
  * минус — N отдельных соединений и N INSERT (см. раздел 12), но для
    нескольких пользователей это несущественно.

getUsersCount() просто возвращает usersRepository.getUsersCount().
findBy-методы так же делегируют в репозиторий.

Почему addUsers(), а не старый addUser(AjaxDto): старый метод принимает один
объект и не знает про age/city/phone. Можно было бы звать его в цикле, но
он не заполняет новые поля, поэтому добавлен отдельный метод, принимающий
готовый список User.


6. ЛИСТЕНЕР И ИНИЦИАЛИЗАЦИЯ ПРИЛОЖЕНИЯ
================================================================================

    @WebListener
    public class CustomServletContextListener implements ServletContextListener {
        public void contextInitialized(ServletContextEvent event) {
            ...
            UsersRepository usersRepository = new UsersRepositoryJdbcImpl(dataSource);
            UsersService usersService = new UsersServiceImpl(usersRepository);

            servletContext.setAttribute("usersRepository", usersRepository);
            servletContext.setAttribute("usersService", usersService);
        }
    }

ВАЖНО: в этой версии листенер НЕ МЕНЯЕТСЯ. usersService уже создаётся и
кладётся в контекст в текущем проекте; новый функционал использует его же.

Почему так:
  * contextInitialized вызывается ОДИН раз при старте приложения;
  * DataSource и репозитории/сервисы создаются один раз, а не на каждый
    запрос — это дешевле;
  * сервлеты получают готовые объекты через ServletContext в init();
  * конфигурация БД (URL, логин, пароль) в одном месте.

Почему @WebListener, а не @WebServlet: @WebServlet регистрирует сервлет,
а не слушатель контекста. С @WebServlet метод contextInitialized никогда не
вызовется, и в контексте не будет атрибутов — сервлеты получат null
(именно такая ошибка была раньше: "signUpService is null").

Альтернативы:
  * прописать <listener> в web.xml — эквивалентно, но аннотация короче;
  * создавать DataSource прямо в init() каждого сервлета — дублирование и
    несколько источников соединений;
  * JNDI-DataSource, настроенный в Tomcat (context.xml) — "правильнее" для
    продакшена, но требует настройки сервера, для учебной задачи избыточно.

DriverManagerDataSource (Spring) здесь просто хранит параметры и открывает
новое соединение на каждый getConnection(). Для учебного проекта этого
достаточно. Важно: сам факт создания DataSource не означает подключение к БД —
оно происходит при первом запросе.


7. SAVESERVLET (ПЕРВЫЙ ПУНКТ ТЗ)
================================================================================

    @WebServlet("/save")

Почему /save: короткий адрес, прямо отражает действие "сохранить"; не
конфликтует с существующими /signUp, /ajax, /users, /profile, /settings.

7.1. init()
--------------------------------------------------------------------------------

    @Override
    public void init(ServletConfig config) throws ServletException {
        usersService = (UsersService) config.getServletContext().getAttribute("usersService");
    }

Почему так, а не init() без параметров: это ровно тот же способ, которым
уже пользуются SignUpServlet, UserServlet и AjaxServlet в проекте. Новых
конструкций не вводим.

7.2. doGet() — шаги 1-2 ТЗ
--------------------------------------------------------------------------------

    int count = usersService.getUsersCount();
    req.setAttribute("count", count);
    req.getRequestDispatcher("/jsp/save.jsp").forward(req, resp);

  * Число берётся из БД (app_settings.users_count) — требование ТЗ.
  * setAttribute кладёт число в request scope, JSP читает его как ${count}.
  * forward (а не sendRedirect), потому что атрибут request живёт только в
    пределах одного запроса: при redirect он потеряется. Побочный эффект —
    в адресной строке остаётся /save, что нормально.
  * Путь /jsp/save.jsp начинается со слэша, то есть от корня контекста.
    Относительный путь зависел бы от текущего URL.

Почему JSP, а не генерация HTML в сервлете: шаблон отделён от кода,
цикл и подстановки делает JSTL, сервлет остаётся коротким.

7.3. doPost() — шаги 3-4 ТЗ
--------------------------------------------------------------------------------

    int count = Integer.parseInt(req.getParameter("count"));
    for (int i = 1; i <= count; i++) { ... }

  * count приходит из hidden-поля формы. Почему не запрашивать БД повторно:
    между GET и POST значение в БД может измениться, и тогда число полей в
    форме и число ожидаемых параметров разойдутся. Hidden-поле фиксирует то,
    что реально было отрисовано.
  * Минус: клиент может подменить count. Для учебной задачи допустимо; в
    реальном приложении значение проверяют/берут из сессии или БД.

Имена полей с индексом:

    firstName_1, lastName_1, email_1, age_1, city_1, phone_1,
    firstName_2, ...

Почему индексы, а не одинаковые имена:
  * одинаковые имена (name="email") браузер отправит как несколько значений,
    и пришлось бы использовать req.getParameterValues("email") — тогда нужно
    синхронизировать порядок значений по всем полям;
  * с индексами явно видно, какие поля относятся к одному пользователю;
  * пустые поля не смешиваются между строками.

Альтернатива с массивами тоже рабочая, но более хрупкая: если пользователь
заполнил не все поля, позиции в массивах разъедутся.

Пропуск пустого email:

    if (email == null || email.trim().isEmpty()) continue;

  * позволяет заполнить не все N форм, а часть;
  * email выбран как "обязательный маркер" строки, потому что он есть в
    форме и в БД;
  * альтернатива — required в HTML и валидация с сообщением об ошибке.
    Сейчас невалидные строки просто не сохраняются, без обратной связи.

Сборка User через builder — читаемо и не зависит от порядка аргументов
конструктора.

parseAge():
  * пустая строка -> null (возраст необязателен), в save() станет 0;
  * type="number" в HTML ограничивает ввод, но серверная проверка всё равно
    нужна: запрос можно отправить в обход формы;
  * try/catch вокруг parseInt не добавлен, чтобы не усложнять код; при
    вводе мусора вручную будет NumberFormatException -> 500. При обычной
    работе через форму этого не случится.

Пароль:

    .password("qwerty007")

  * форма из ТЗ не спрашивает пароль, а колонка password, скорее всего NOT NULL;
  * поэтому подставляется значение по умолчанию, как уже сделано в
    UsersService.addUser().
  * Альтернативы: добавить поле пароля в форму; генерировать случайный;
    хешировать через BCryptPasswordEncoder (он уже есть в проекте из-за
    spring-security). Для ДЗ оставлено простое значение, но в реальном коде
    пароль в открытом виде хранить нельзя.

Сохранение и редирект:

    usersService.addUsers(users);
    resp.sendRedirect(req.getContextPath() + "/html/saved.html");

  * Редирект — требование ТЗ ("достаточно выполнить редирект на другую
    страницу, любую").
  * req.getContextPath() возвращает /servlets_war. Если написать
    sendRedirect("/html/saved.html"), браузер уйдёт на localhost:8080/...
    мимо приложения и получит 404. Именно на этом уже ломались форма signUp
    и AJAX-запрос.
  * Редирект после POST — это паттерн Post/Redirect/Get: при обновлении
    страницы (F5) браузер повторит GET, а не POST, и пользователи не
    добавятся второй раз.
  * sendRedirect заставляет браузер сделать новый запрос, поэтому URL
    меняется на /html/saved.html.

Почему не forward на saved.html: после POST остался бы URL /save, и F5
предложил бы повторно отправить форму.

Обработка SQLException:

    catch (SQLException e) { throw new ServletException(e); }

  * ServletException — штатный способ сообщить контейнеру об ошибке в
    сервлете; Tomcat отдаст 500 и запишет стектрейс в лог.
  * Альтернатива — показать пользователю страницу ошибки (error-page в
    web.xml). Для ДЗ достаточно 500 + лог.


8. SAVE.JSP
================================================================================

    <%@ taglib prefix="c" uri="http://java.sun.com/jsp/jstl/core" %>
    <c:forEach begin="1" end="${count}" var="i">
        ...
        <input name="firstName_${i}" placeholder="First name">
    </c:forEach>

Почему JSTL, а не scriptlet (<% for ... %>):
  * JSTL уже используется в проекте (jsp/users.jsp, <c:forEach>);
  * нет Java-кода в шаблоне;
  * EL-выражения короче и читаемее, чем <%= %>;
  * примечание: ${...} НЕ экранирует HTML автоматически; если значение
    приходит от пользователя и выводится как HTML, нужно <c:out> или
    function:escapeXml.
  * легче читать.

Почему begin="1", а не "0": индексы 1..N совпадают с номерами "Пользователь 1",
и в сервлете цикл тоже начинается с 1. Меньше шансов на ошибку "на единицу".

Почему hidden count:
  * сервлет на POST знает, сколько строк было отрисовано;
  * значение приходит вместе с формой и не зависит от повторного SELECT.

Почему action="${pageContext.request.contextPath}/save":
  * context path подставляется автоматически, ссылка не сломается при смене
    контекста;
  * в обычном .html так нельзя (EL там не выполняется), поэтому в статических
    страницах пути пишут вручную или относительно.

type="number" у age:
  * браузер не даст ввести буквы;
  * на мобильных откроется цифровая клавиатура;
  * это удобство, а не замена серверной валидации.

Placeholder'ы на английском — по вашему запросу; на работу формы не влияют.


9. SAVED.HTML

    <h1>Пользователи добавлены</h1>

  * Статическая страница-подтверждение, как разрешено в ТЗ.

10. SELECTSERVLET (ВТОРОЙ ПУНКТ ТЗ)
================================================================================

    @WebServlet("/selects")

Почему отдельный сервлет: ТЗ прямо требует "используя отдельный сервлет с
консолью". Плюс это отдельный сценарий: чтение, а не запись.

doGet, а не doPost:
  * выборка ничего не меняет, GET идемпотентен;
  * запрос можно открыть в браузере и перезагружать без последствий.

Значения захардкожены:

    findByCity("Казань")
    findByAgeGreaterThan(18)
    findByPhone("+79000000000")

  * это самый простой вариант "отдельный сервлет с консолью";
  * параметры из URL не нужны, меньше кода — меньше вопросов;
  * если понадобится проверять другие значения, достаточно поменять строку
    в коде и перезапустить, либо добавить req.getParameter (метод уже
    используется в SaveServlet).

Почему init(ServletConfig): как в остальных сервлетах проекта.

Вывод:

    System.out.println("=== " + title + " ===");
    ...
    resp.getWriter().println(line);

  * System.out.println — это и есть "консоль" из ТЗ: вкладка Run в IntelliJ
    или catalina/localhost лог Tomcat;
  * дублирование в ответ text/plain добавлено для удобства проверки из
    браузера; при желании можно убрать и оставить только консоль.

Почему text/plain, а не HTML:
  * это отладочный вывод, а не страница;
  * браузер не интерпретирует строки как разметку;
  * не нужно экранировать данные.

Приватный метод print() вынесен, чтобы одинаково форматировать три выборки
и не копировать цикл три раза.

Почему не JSP: ТЗ просит консоль; JSP с SQL — смешение слоёв.

Почему не в SaveServlet: ТЗ требует отдельный сервлет; плюс разные URL
удобнее проверять.

Альтернативы:
  * параметры в query string (?city=...&age=...&phone=...) — гибче, но
    больше кода;
  * один сервлет /selects с HTML-формой — удобнее для пользователя;
  * JSON API и отдельная страница — ближе к реальным приложениям;
  * вызвать выборки в contextInitialized и напечатать при старте — плохо:
    результат теряется в логах запуска и нет явной демонстрации.


11. ПОЧЕМУ НЕ СДЕЛАНО ИНАЧЕ (СВОДКА АЛЬТЕРНАТИВ)
================================================================================

  * Число из БД:
      + app_settings (выбрано) — данные, меняются без пересборки;
      - константа в коде — не соответствует ТЗ;
      - count(*) — это число существующих, а не добавляемых;
      - properties-файл — не БД.

  * Где метод получения числа:
      + в UsersRepository (выбрано) — не плодим лишние интерфейсы;
      - отдельный SettingsRepository — чище по SOLID, но лишняя сущность
        для одного метода;
      - SQL прямо в сервлете — смешение слоёв.

  * Передача count в POST:
      + hidden-поле (выбрано) — просто, соответствует отрисованной форме;
      - повторный SELECT — значение может измениться между запросами;
      - сессия — надежнее, но усложняет код.

  * Имена полей:
      + индексы firstName_1 (выбрано) — явная связь полей;
      - одинаковые имена + getParameterValues — хрупко при пустых значениях.

  * Вставка N записей:
      + цикл save() (выбрано) — только уже известные методы;
      - addBatch/executeBatch — эффективнее, но этого не было в проекте;
      - динамический multi-row INSERT — быстрее, но сложнее.

  * Три выборки:
      + три явных метода (выбрано) — требование ТЗ, читаемо, безопасно;
      - универсальный findBy(column, value) — риск инъекции через колонку.

  * Куда сохранять и как показать результат:
      + redirect на статическую страницу (выбрано) — PRG, требование ТЗ;
      - forward — F5 повторяет POST;
      - вывод числа на странице — ТЗ не требует.

  * Где хранить зависимости:
      + ServletContext + listener (выбрано, уже было в проекте);
      - поля-синглтоны/статика — тяжелее тестировать;
      - создание в каждом сервлете — дублирование и лишние соединения.

  * Доступ к БД:
      + JDBC + PreparedStatement (выбрано) — соответствует курсу;
      - JPA/Hibernate — мощнее, но лишний слой для ДЗ;
      - Spring JdbcTemplate — короче, но проект уже использует чистый JDBC.

  * JSP:
      + JSTL (выбрано) — уже применяется в users.jsp;
      - scriptlets — быстрее написать, хуже поддерживать.

  * Закрытие ресурсов:
      + try-with-resources (выбрано) — Connection/Statement/ResultSet
        закрываются автоматически даже при исключении;
      - ручной close() в finally — длиннее и легче забыть.


12. ЧТО ОСОЗНАННО НЕ ИСПОЛЬЗОВАНО И ПОЧЕМУ
================================================================================

Код специально ограничен средствами, которые уже встречались в проекте до ДЗ.
Исключения (используются, потому что без них код был бы некорректен):
  * try-with-resources — JDBC-ресурсы (Connection, Statement,
    PreparedStatement, ResultSet) закрываются автоматически в обратном
    порядке даже при исключении. В исходном коде проекта ресурсы не
    закрывались — здесь этот недостаток исправлен.
  * приватный метод userFromResultSet() — просто вынесенный общий код
    преобразования строки ResultSet в User, чтобы не копировать его.

Не использованы:

  1) addBatch() / executeBatch()
     Причина: в исходном UsersRepositoryJdbcImpl вставка делалась одним
     executeUpdate(). Батч ускоряет массовую вставку, но это новая тема.
     Замена: цикл по пользователям + save().

  2) setNull() / wasNull()
     Причина: в проекте не встречались. Замены:
       - при записи: setInt(5, age == null ? 0 : age);
       - при чтении: getString("age") + Integer.parseInt.

  3) Collections.singletonList() и saveAll()
     Причина: не было в проекте. Замена: отдельный save() на каждого
     пользователя, вызов из сервиса в цикле.

  4) Отдельный SettingsRepository
     Причина: ради одного метода создавать интерфейс и реализацию — лишние
     файлы и лишняя сущность. Метод getUsersCount() добавлен в UsersRepository.

  5) Параметры URL в SelectServlet (req.getParameter для city/age/phone)
     Причина: для демонстрации достаточно констант. getParameter в проекте
     есть, так что при желании добавить несложно.

  6) Хеширование пароля, валидация, обработка ошибок страницей
     Причина: не требуется ТЗ и не было в проекте. Отмечено в ограничениях.


13. ОГРАНИЧЕНИЯ ТЕКУЩЕГО РЕШЕНИЯ
================================================================================

Это важно знать, чтобы не выдать учебный код за продакшн:

  1) count приходит из hidden-поля и может быть подменён клиентом.
     В реальном приложении его берут из сессии/БД и ограничивают сверху.

  2) Пароль хранится в открытом виде ("qwerty007"). В проекте уже есть
     BCryptPasswordEncoder — правильнее хешировать.

  3) Нет проверки уникальности email и вообще валидации полей. Если в БД
     есть UNIQUE(email), дубликат приведёт к SQLException -> 500.

  4) Нет обработки ошибок с показом пользователю: любая проблема с БД даёт
     500 и стектрейс в логе.

  5) Вставка N пользователей не обёрнута в транзакцию: если одна строка
     нарушит ограничение, предыдущие уже могут быть записаны.

  6) Connection/Statement/ResultSet закрываются через try-with-resources —
     это корректно. Но DataSource всё равно без пула: каждое соединение
     открывается заново (см. пункт 7).

  7) DataSource — DriverManagerDataSource без пула. Под нагрузкой каждое
     соединение открывается заново; в реальном приложении — HikariCP или
     JNDI-пул Tomcat.

  8) SelectServlet печатает данные в консоль и отдаёт text/plain. Если
     поменять на HTML, понадобится экранирование, иначе XSS.

  9) В UsersRepositoryJdbcImpl пароль и email попадают в объект User и,
     если сериализовать его в JSON (как в AjaxServlet), пароль уйдёт
     клиенту. Для JSON нужен @JsonIgnore на password или отдельный DTO.

 10) SQLException заворачивается в ServletException, из-за чего в логе
     видно обёртку "ServletException: org.postgresql.util.PSQLException".
     Для отладки удобно смотреть "Caused by".

 11) Возраст не указан -> в БД 0, а не NULL. На выборку age > 18 это не
     влияет, но в таблице будет 0.
